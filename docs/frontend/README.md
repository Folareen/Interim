# Frontend rules

Next.js App Router PWA in `apps/web`, mobile first. Pages and flows: [architecture.md](../architecture.md) section 10. Visual rules: [design-system.md](design-system.md). Code style: [../typescript.md](../typescript.md).

## Conventions
- Server components by default. Add `'use client'` only for state, effects, camera or browser APIs, and keep those components small.
- The browser only calls `/api/*`, which the web server forwards to the API (`API_ORIGIN`, server side only), so the session and owner cookies are first party. No YouCam or LLM keys or calls from the browser.
- Validate API responses with the zod schemas from `@interim/types` at the fetch boundary; pass typed data down.
- Capture checks (angle, light, resolution) run on the device and block upload on failure. They are advisory; the server checks again.
- Photos upload straight to storage through presigned links from the API.
- Test the camera and install flow on iOS Safari and Android Chrome.

## Screens and state
A new person goes welcome, sign up, then situation, setup (tone, head covering, age), consent and ready; the three steps after sign up show a progress line. Someone signed in who opens `/` goes straight to where they left off: situation with no profile, Today for the first profile with current consent, otherwise consent for the first profile. The situation switcher opens the other owned profiles. Language is not a step: it follows the browser until the person uses the globe in the header. Sign in lives at `/signin`, `/signup`, `/magic`, `/forgot`, `/recover`, `/reset` and `/auth/confirm`, the signed in person's page is `/account`, and `/settings/[id]` changes tone and head covering after setup. The API sets the `interim_session` cookie; the web app only checks it exists before asking `/auth/me`, so a signed out visit makes no extra call. An emailed link opens `/auth/confirm` or `/reset`, and a link is spent only when its button is tapped, never on load. Google sign in is a plain link to `/api/auth/google/start`, shown only when the API reports it is on. Every screen after sign up redirects to sign in when there is no session. The language and theme live in cookies (`interim_locale`, `interim_theme`) that the server reads, so pages render in the right language and theme from the first paint. Before a language is chosen, the browser's `Accept-Language` picks one the app offers, else English, and nothing is stored until the person chooses. A globe button in the header opens the language screen from any page and brings the person back to where they were. The situation travels in the address of the setup step. The profile is created, under the signed in account, when setup is submitted, and later screens read it by id on the server with the person's cookie. The language and situation screens are plain forms and work without JavaScript.

After consent, the shared workspace has three destinations: Today (`/ready/[id]`), My looks (`/looks/[id]`) and You (`/you/[id]`). Mobile uses a labelled bottom navigation; desktop uses a sidebar and a wider content area. Both include an owned-situation switcher. Today puts a single update action first, the latest result alongside it on desktop, and offers reflection as a quiet row and words only when enabled. Returning visits use a short greeting without a repeated introduction. An unfinished latest run resumes rather than starting another update. My looks pages six visual results at a time in a two-column mobile photo gallery. You shows compact Sign out beside its heading, with preference and account rows and an expandable data section for ledger, export and deletion; destructive controls stay out of the daily flow. The account page also offers Sign out immediately below the email; signing out ends this browser’s session and keeps saved profiles.

An update opens `/update/[id]`. Fit templates with body photos enabled first offer saved clothes, with a direct continuation even when nothing is selected. Other profiles go straight to `/capture/[id]`. The capture wizard asks for changes, reported size where relevant and an optional moment before the photos. It still follows `capturePlan`, checks each photo on the device and sends them straight to storage. Submission starts a run and opens `/runs/[id]`, which follows its event stream and opens `/cards/[id]` when ready. The Camera Kit script is loaded only on capture; the file input remains available when it fails or permission is refused.

The Stage Card leads with previews and its short note. Changes, shopping, advice, sharing and trace use labelled expandable sections. Its optional help offers translated topic buttons without a model request. When the API reports written help available, a question requires a separate Google disclosure and checkbox for each message. Only a bounded topic identifier returns; reviewed UI text and recorded measurements provide the answer, never model prose. Questions do not start renders or change settings. The input is not a stored conversation. See [llm.md](../llm.md#optional-result-help).

`/clothes/[id]` remains the fit catalog. `/ledger/[id]` reads the owner-protected endpoint through `ledgerViewSchema`, with separate held and spent totals and individual reserve, settle and release events. `/you/[id]` links to `/api/profiles/[id]/export.zip` as a native download link. A client island can read only namespaces passed by `app/layout.tsx` to `NextIntlClientProvider`.

From the ready screen, "Reflection" opens `/reflect/[id]`: one prompt, a text box, the saved reflections with a delete on each, and a permanent "Need to talk to someone?" link. The device runs the exact crisis check before it sends, so the contacts card (`CrisisContacts`, region from the browser, changeable) shows at once; the server checks again. A flagged profile also shows the card on the ready screen until the person closes it. The Stage Card offers the screen after a check in that reports a lot of change.

Words for today is chosen on the settings screen (off, or one of four sets). While it is on, the ready screen shows today's passage with its source and translation, fetched with the person's local date so it turns over at their midnight. When the set has no translation in their language the passage is English and a note says why.

The Stage Card makes share links (`ShareCard`): a new link is shown once with a copy button, because the API keeps only a hash, and later visits list the links that still work with a stop button each. `/s/[token]` is the share view for someone signed out. It calls the API without the person's cookie, answers 404 for a link that is unknown, expired or revoked, and sets `noindex` and `no-referrer`.

The public welcome page tells the product story separately from the workspace: everyday appearance problems, two illustrated audience groups covering all eleven situations, photo-to-result steps, factual differences from general AI chat and expandable privacy/usage questions. It reuses the neutral situation descriptions and clearly labels synthetic imagery. It makes no comparative performance claims, medical promises, free-tier claims or unverified prevalence claims. Landing copy stays server-rendered in its own translated namespace, with direct headings and no repeated eyebrow labels. A small client island adds one-time viewport entrances through Web Animations and IntersectionObserver; it never gates rendering or navigation and cancels active animations when reduced motion is requested.

`/demo` is open to anyone and lists the sample people with their check ins; `/demo/cards/[id]` shows one recorded card. Both are server components that call the API without the person's cookie, and the card page renders the same `StageCardBody` as `/cards/[id]` with nothing that changes data. The welcome screen links to it.

`/privacy` and `/terms` are public server-rendered pages linked from the shared footer, including before signup and consent. Privacy reuses the consent catalog’s processor and photo-retention wording. The public contact address lives in the message catalogs and is the same in every language. An optional `SUPPORT_EMAIL` deployment override is validated by the web server; an unset or empty override uses the catalog address. The pages describe the implemented prototype, and the wording still needs the review tracked in spec section 17.

Before a screen is done, check it in both themes at 320px and 390px wide, with the keyboard only, and with an axe audit that reports no violations.

## Copy
User facing strings follow the language rules in [../product/overview.md](../product/overview.md) and are scanned with `@interim/rules`.

The app uses [next-intl](https://next-intl.dev). The server reads the person's language in `i18n/request.ts` and every page gets that language's messages. Server components call `getTranslations('namespace')` and client components `useTranslations('namespace')`. Keys are typed from the English file (`global.d.ts`), so a key that does not exist fails the typecheck.

**Translations move with the frontend.** No text is written inline in a component. Every string lives in `packages/templates/src/messages/<locale>.json`, one file per language, with the same keys in every file. Any frontend change that adds, edits or removes text updates all ten files in the same pull request, not only English:
- Add the key to `en.json` first, then to the other nine. `copy.test.ts` fails if a language has a missing or extra key, an empty string, or different `{marks}` from English.
- The same test runs the banned word and companion phrase scans on every string in every language, so a new string is covered with no list to update.
- Put a value into a sentence with a mark such as `{current}`, never by joining fragments, so word order can differ between languages. Keep numbers, dates and sizes out of the text and pass them in. Write a curly apostrophe (’) rather than `'`, because next-intl treats a straight one before `{` as an escape.
- Every language is written with care and checked against verified sources where unsure; none is labelled a draft. Words for today live in `words/<locale>.ts`, and a set with no public domain translation falls back to English.
- The `Messages` type in `packages/templates` is what the API reads for fixed notes, situation names and the lines for what to say, so the API and the web app never keep separate copies.

## Accessibility
Every control is keyboard reachable and labelled; contrast meets WCAG AA; do not rely on color alone; respect reduced motion. The page's `lang` is the person's language, a language's own name carries its own `lang` on the language screen, a button that is off says why through `aria-describedby`, and a status line announces when a form is working. The theme and language buttons are labelled by what they do.

The screen reader pass (VoiceOver and TalkBack testing) comes after the core flow works end to end. Until then the basics above still apply to every component.

## PWA
`app/manifest.ts` defines the manifest. `public/sw.js` is the service worker; it only shows pushes, which the server writes in the person's language (spec section 12a). Icons are still to add.
